# 智维Agent —— 面向工序设备的多模态故障诊断与自主维保决策智能体

一句话介绍：面向制造企业设备维保依赖人工经验、故障预警与维修执行脱节的问题，
构建融合**工业风险预测模型**、**可解释性分析**、**设备维修知识库**和**大模型工具调用**的维保智能体，
实现从异常监测、故障诊断、原因解释、维修决策到**工单生成与效果复核**的自主闭环。

> 数据来源：UCI SECOM 半导体前道工序数据集（id=179，1567 批次 × 591 路工艺信号，CC BY 4.0）。
> 本项目不是"聊天机器人套壳"：每一次诊断都是真实的 Python 工具调用，每个结论都能追溯到具体批次、具体信号、具体知识条目。

## 3. 系统架构

### 3.1 主 Agent + 6 个工具

不做"七八个 Agent 互相聊天"这种在赛场上很难讲清楚的结构，而是**一个主 Agent + 6 个真实工具**：

| 工具 | 作用 | 实现位置 |
|---|---|---|
| `get_sensor_data(lot_id)` | 查询批次的工艺信号快照，计算相对训练分布的标准分偏差 | `tools.py` |
| `predict_failure(lot_id)` | 调用风险模型，输出异常概率、等级、触发阈值 | `tools.py` + `model.py` |
| `explain_failure(lot_id)` | SHAP 解释：是哪几路信号把风险推高、归属哪个工序站 | `tools.py` + `explain.py` |
| `search_maintenance_manual(query)` | 检索维修知识库，返回带出处的维修依据 | `tools.py` + `rag.py` |
| `simulate_maintenance_decision(lot_id)` | 模拟"立即检修 / 延时检修 / 继续生产"三种方案的期望代价 | `tools.py` |
| `create_work_order(...)` | 在业务数据库中真实新增维修工单 | `tools.py` + `db.py` |

### 3.2 LangGraph 执行图

```
START → parse_intent ─┬─ scan_stream ────────────────────────────────────────→ finalize
                      └─ fetch_sensor → predict_failure → [风险分支]
                                                           ├─ 低风险 → low_risk_report → finalize
                                                           └─ 高风险 → explain_failure
                                                                     → retrieve_manual
                                                                     → simulate_decision
                                                                     → propose
                                                                     → human_review ← 人工确认（interrupt）
                                                                          ├─ 同意 → create_work_order → finalize
                                                                          └─ 拒绝 → handover_human → finalize

每个工具节点后都接一个 retry 守卫：
    工具抛异常 → retry 节点（计数 +1）→ 回到原节点；超过 N 次 → handle_error
```

图上直接体现了比赛要求的六件事：

1. **能看到每一步干了什么** —— 执行轨迹记录了工具名、参数、返回、耗时、第几次调用；
2. **真正调用自己写的 Python 函数** —— 6 个工具都是普通 Python 函数，返回结构化结果；
3. **条件分支** —— 风险高低走不同路径；人工同意与否走不同路径；
4. **保留任务状态** —— `AgentState` + `MemorySaver` 检查点，按 `thread_id` 恢复；
5. **人工确认** —— `human_review` 节点用 LangGraph `interrupt()` 暂停，界面点"确认"后 `Command(resume=...)` 继续；
6. **失败重试** —— 可控故障注入（`--fail-first` / 界面下拉框）现场演示重试分支。

## 4. 数据集：UCI SECOM

官方事实（已核对 UCI 数据集页面与 API）：

| 项目 | 值 |
|---|---|
| 样本数 | 1567 个生产实体（每个 = 一个批次） |
| 变量数 | 591 路传感器 / 过程测量点 |
| 标签 | `-1` = 良品，`+1` = 异常；异常 104 条，占比 **6.64%** |
| 时间戳 | 随标签给出，跨度 2008-07-19 → 2008-10-17 |
| 缺失值 | 存在，共 43518 个 NaN，全部 1567 行都含缺失 |
| 变量含义 | **匿名**，官方未公开每个变量的物理含义 |
| 许可 | **CC BY 4.0**（可商用、可改造，只需署名）——比赛使用无许可障碍 |

### 两个必须提前想清楚的问题

**① 变量匿名，怎么讲"故障定位"？**
本项目用相关性层次聚类把 591 路匿名变量归并为 12 个**工序信号簇**，命名为"工序站 A–L"。
当一个批次异常时，智能体说的是"异常集中在工序站 C，主要贡献信号是 var_489 / var_104"，
而不是编造"刀具磨损"这类没有依据的物理结论。**这是可核验的表述，答辩时经得起追问。**

**② 时间漂移很严重，怎么办？**
见第 5 节，这是一个真实发现，也是项目可以写进答辩的加分点。

## 5. 模型与评估

### 5.1 建模流程

1. 剔除训练集中的常量列（591 → 468 路有效信号）；
2. 缺失值用训练集列中位数填补（只用训练集统计量，避免泄漏）；
3. 相关性聚类得到工序站映射；
4. XGBoost（`max_depth=3, colsample_bytree=0.3, min_child_weight=5, reg_lambda=2.0`），
   超参由 `experiments/tune_model.py` 的对比实验选出（结果写入 `artifacts/tuning_results.csv`）；
5. **上线模型 = 5 个自助采样（80% 子样本）模型的概率平均**。
   单个模型在全量数据上重训会把历史批次评分压成 0/1 两档，取平均后分布平滑、也更接近新批次表现；
6. 阈值取**袋外预测上 F1 最优**的点；历史批次一律用**袋外评分**展示，避免样本内乐观偏差。

### 5.2 指标（重点不是 Accuracy）

异常占比仅 6.64%，因此用 PR-AUC / Recall / F1 而不是 Accuracy。

| 协议 | PR-AUC | ROC-AUC | Recall | Precision | F1 |
|---|---|---|---|---|---|
| **主协议**：分层 5 折交叉验证（袋外预测） | **0.175** | 0.712 | 0.337 | 0.199 | 0.250 |
| 漂移检查：按时间切分留出集 | 0.067 | 0.573 | 0.000 | 0.000 | 0.000 |

主协议下 PR-AUC 0.175 ≈ 基准不良率（0.066）的 **2.6 倍**；
按袋外评分排序，"高"档批次的真实异常率约为基准的 3.5 倍。
这与学术界在 SECOM 上的公开结果区间一致（该数据集的 ROC-AUC 通常在 0.7~0.85、PR-AUC 在 0.1~0.25）。

### 5.3 一个真实发现：时间漂移

按时间切分后模型几乎失效（PR-AUC 掉到 0.067，等于随机），说明**这台产线的工艺状态在三个月内发生了明显漂移**，
用早期数据训练、预测后期批次会系统性失准。

这不是代码 bug，而是工业数据的常态，也是本项目在答辩中值得讲的一段：

> 我们没有只报一个好看的交叉验证分数，而是同时做了时间留出集检验，
> 发现了明显的时间漂移，因此在上线设计上采用**滚动重训 + 阈值在线校准 + 人工确认兜底**，
> 而不是让模型直接自动放行。

> 说明：以上参数为演示假设值，决策结果为模拟估算，不代表真实企业收益。

## 6. 现场演示脚本（建议）

**第 0 步：展示界面结构**——监控区、执行轨迹区、决策工单区、知识库、模型评估，五个区域都在，不是一个光秃秃的聊天框。

**第 1 步：让评委任意点一个批次**，或直接用系统自动选中的高风险批次（如 `LOT-1401`）。

**第 2 步：点"运行诊断"**，指着执行轨迹念：

1. 读取 468 路有效工艺信号，9 路超过 3σ，偏差最大的工序站是 A；
2. 风险模型给出 **80.8%**，高于触发阈值 15%，等级"高"；
3. SHAP 解释：var_022 +0.22、var_104 +0.20、var_103 +0.15 把风险推高；
4. 检索知识库，命中《过程参数漂移排查指南》第 1/2/3 节；
5. 三方案模拟：立即检修期望代价 ¥9,736，比最差方案省 ¥31,608，推荐**立即停机检修**。

**第 3 步：强调"这不是大模型编的"**——每一步都有参数、有返回值、有耗时，可以点开 JSON 展开看。

**第 4 步：人工确认**——智能体在 `human_review` 处暂停，等工程师点确认，现场说一句：
"工业场景不能让 AI 直接停机，所以这里强制人工确认。"

**第 5 步：展示工单落库**——点确认后，SQLite 里立刻出现 `WO-YYYYMMDD-NNN`，
含批次、工序站、优先级、风险值、建议动作、负责人、备件、计划完成时间、状态。

**第 6 步：演示失败重试**——在下拉框选择 `search_maintenance_manual` 制造一次工具故障，
重跑一次，让评委看到第 4 步失败、进入 retry 节点、第 5 步成功，流程自动恢复。

**第 7 步（可选）：断网演示**——不配 API Key 时走离线规则模式，全流程依然跑通，
说明系统不依赖外部服务。

## 8. 进阶扩展

**接入大模型（Qwen / DeepSeek）**：复制 `.env.example` 为 `.env` 或直接设环境变量：

```bash
OPENAI_API_KEY=sk-xxx
OPENAI_BASE_URL=https://api.deepseek.com/v1     # 或 dashscope 兼容模式地址
ZHIXI_LLM_MODEL=deepseek-chat
```

设置后，意图解析与最终结论由大模型生成；**关键判断（风险值、阈值、工单内容）仍由确定性代码产出**，
避免大模型"猜"出没有依据的结论。未配置时自动走离线规则模式。

**换成真正的向量库**：`pip install faiss-cpu` 后重启，`rag.py` 会自动切换到 FAISS 向量索引；
若要换成 bge-m3 / text-embedding 等嵌入模型，只需替换 `rag.py` 里的 `_vectorize` 部分。

**加入声音多模态**：工具层已经预留位置——增加一个 `analyze_acoustic(file)` 工具，
把声学异常分与工艺信号一起交给 `explain_failure`，即可升级为"多模态工业 Agent"。

**换成 AI4I 2020 数据集**：AI4I 的变量有明确物理含义（空气温度、过程温度、转速、扭矩、刀具磨损），
适合讲"刀具磨损"这类归因叙事；SECOM 的优势是真实、高维、脏数据。两者可以并用：
AI4I 讲清楚机理，SECOM 证明鲁棒性。

## 11. 常见问题

**Q：为什么有的批次风险是 0.2%，有的是 98%？**
SECOM 本身可分性有限，模型的输出分布天然是长尾的；再加上上限集成，绝大多数批次接近基线，
少数批次显著偏高。这符合工业预警的实际情况——**大部分时间风平浪静，少数时候要报警**。

**Q：为什么"立即停机检修"总被推荐？**
在默认业务参数下，异常批次的期望质量损失高于停机成本，经济学上就该停机。
在左侧把"停机损失"调高、或把"单批次产值"调低，你会看到推荐结果随之改变——**决策是算出来的，不是写死的**。

**Q：风险高就一定要停机吗？**
不一定。低于触发阈值时智能体走的是"低风险放行 + 趋势观察"分支，不生成工单；
只有超过阈值才进入完整决策链路，且最终仍需人工确认。
